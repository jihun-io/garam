# Garam 로드맵

> 각 마일스톤은 "동작하는 앱"으로 끝난다. 완료 조건을 모두 만족해야 다음 단계로 넘어간다.
> 마일스톤 순서는 의존 관계를 따른다. 진행하면서 체크박스를 갱신한다.

## M2. 변경 사항과 커밋

- [x] status 파서 + 파일 목록 (가상 스크롤, 키보드 이동·Space로 포함/제외)
- [x] 파일 감시 → 자동 새로고침 (`.git` 내부는 index·HEAD·refs 변경만 반영)
  - Linux에서 변경이 없어도 새로고침이 멈추지 않던 문제를 고쳤다. inotify는 파일을 열고 닫는 접근 이벤트까지 보내는데, 새로고침이 실행하는 `git status`가 작업 폴더 파일을 열면 그 이벤트가 다시 새로고침을 불렀다. 이제 접근 이벤트는 무시한다. 2026-10-28 Ubuntu 26.04(커널 7.0, UTM) 실제 앱에서 파일 50개짜리 저장소를 열어 두고 `git status` 호출을 셌다. 고치기 전에는 아무것도 바꾸지 않아도 10초에 31–32회(초당 약 3회, git 호출 전체로는 40초에 약 3,300회) 돌았고, 고친 뒤에는 0회, 파일 하나를 바꾸면 1회다. 재현 프로그램으로도 Ubuntu 26.04에서 10초에 39회 → 2–3회, Docker(ubuntu:24.04)에서 37회 → 2회였다. macOS는 접근 이벤트가 없어 동작이 같다
- [x] diff 파서 + diff 뷰어 (텍스트, 이미지 전후 비교, 바이너리, 너무 큰 diff)
- [x] 파일 단위 스테이징·언스테이징 (전체 선택 포함, 이름 변경은 양쪽 경로 함께)
- [x] 변경 취소 (확인 대화상자, 현재 내용은 휴지통으로 이동)
  - 파일 수만 개를 한꺼번에 취소할 때 macOS에서 초당 8개 정도만 옮겨지던 문제를 고쳤다. `trash` 크레이트의 Finder 방식은 호출마다 `osascript`를 띄우고, 한 번에 여러 파일을 넘겨도 Finder가 항목을 하나씩 처리한다(500개에 약 6초). 그래서 고른 파일만 들어 있는 디렉터리는 디렉터리 하나로 넘기고(500개가 든 디렉터리도 0.2초 안쪽), 나머지는 500개씩 묶어 보낸다. 추적 중이거나 무시된 파일, 고르지 않은 파일이 섞인 디렉터리는 묶지 않는다. 2026-10-28 macOS 실제 앱에서 파일 3만 개로 확인함
- [x] 커밋 (요약·설명, IME 처리), amend, Co-authored-by. 직전 커밋의 파일·줄을 다시 고르는 편집 화면은 아래 "커밋 다듬기"에서 보강했다
- [x] Git 사용자 정보가 없을 때 설정 유도

**확인함**(2026-10-23, macOS·Windows 실제 앱): 변경 취소 시 휴지통으로 이동, 이미지 전후 비교.

**남은 확인**: Linux에서 같은 항목.

## M5. 원격 동기화

- [x] fetch/pull/push + 진행률 (pull은 fetch 단계만 취소 가능, 리베이스·ff-only 설정 존중)
- [x] ahead/behind 표시, publish (업스트림이 원격에서 삭제된 브랜치 포함)
- [x] askpass 헬퍼 + 앱 내 자격 증명 프롬프트 (HTTPS, SSH 암호, SSH 호스트 키 확인)
- [x] 백그라운드 fetch (5분, 프롬프트 없음 — 주기 설정은 M8)
- [x] non-fast-forward, 인증 실패 등 오류 안내
- [x] 커밋하지 않은 변경 사항 때문에 풀이 멈추면 "변경 사항을 잠시 보관하고 풀하기"를 제안(`--autostash`, 병합·리베이스 모두). 다시 꺼낼 때 충돌하면 보관한 내용은 스태시(autostash)에 남기고 충돌 배너로 이어진다. git은 병합할 때 스테이지된 변경 사항이 하나라도 있으면 겹치는 파일이 없어도 거부한다
- [x] 틀린 암호 안내: ssh는 키 암호를 같은 문구로 세 번까지 묻기 때문에, 한 작업에서 같은 프롬프트가 다시 오면 "입력한 암호가 맞지 않습니다"를 보여 준다. SSH 키 암호 창에는 자격 증명 도우미 안내 대신 "SSH 에이전트에 키를 추가해 두지 않으면 매번 묻는다"를 보여 준다(도우미는 HTTPS만 기억한다)
- [x] "이 컴퓨터에 기억": 모든 호스트에 쓰는 credential helper가 없을 때(Linux에서 흔함) 암호 입력 창에 체크박스(기본 켬)를 보여 주고, 인증에 성공한 값만 OS 키체인에 저장해 다음부터 묻지 않는다. 거부되면 저장한 값을 지운다. 설정 > 계정에서 기억한 로그인을 보고 지운다(ARCHITECTURE.md 2.7). helper가 있으면(macOS·Windows 기본) 지금처럼 그 helper에 맡기고 체크박스는 없다

**확인함**(2026-10-23, macOS 릴리스 빌드 rc.2, 로컬 시험 서버): SSH는 처음 보는 호스트 키 확인, 암호 걸린 키의 암호 입력, 다시 푸시할 때 암호만 묻기, 세 번 틀리면 인증 실패 안내까지. HTTP Basic 인증(사용자 이름 + 토큰)은 가져오기·푸시, 틀린 토큰, 취소까지. GitHub 계정 로그인(Device Flow)과 키체인 저장, 그 계정으로 푸시도 확인했다. "이 컴퓨터에 기억"은 개발 빌드에서 helper를 비운 저장소로 확인했다.

**확인함**(2026-10-23, Windows 11 ARM의 UTM 가상 머신, 릴리스 워크플로를 손으로 실행해 만든 x64 NSIS 빌드, Mac에 띄운 시험 서버): GUI 서브시스템 실행 파일이 askpass와 credential helper로 실행될 때 답을 git에 제대로 넘긴다. HTTP 토큰 로그인과 "이 컴퓨터에 기억"(Windows 자격 증명 관리자), SSH 키 암호와 처음 보는 호스트 키 확인 모두 동작했다. Git for Windows는 Git Credential Manager를 기본으로 켜 두므로, Garam 창이 뜨려면 저장소에서 `credential.helper`를 비워야 했다(GCM이 있으면 GCM이 로그인을 맡는다)

**남은 확인**: Linux에서의 로그인(대개 helper가 없어 "이 컴퓨터에 기억"이 실제로 쓰이는 환경, Secret Service가 없을 때 키체인 저장이 실패하면 어떻게 보이는지 포함).

## M8. 마무리와 첫 릴리스 (v0.1.0)

**v0.1.0 공개**(2026-10-23): `v0.1.0` 태그의 릴리스 워크플로가 세 OS 모두 성공했고, 초안을 공개해 GitHub의 최신 릴리스가 되었다. 올라간 파일은 macOS 유니버설 DMG와 업데이트용 `.app.tar.gz`, Windows NSIS 설치 파일, Linux AppImage·deb, 각각의 `.sig`, `latest.json`이다(MSI 없음). 업데이트 피드(`releases/latest/download/latest.json`)가 `0.1.0`과 세 OS 항목으로 응답한다.

UI 개선은 `docs/UI.md` 계획(1~6단계)을 따른다.

- [x] 설정 화면 (언어, 테마, Git 사용자 정보, 에디터·터미널, fetch 주기) — UI 3단계
  - 언어를 바꾸고 다시 시작하면 macOS가 직접 넣는 메뉴 항목까지 그 언어로 바뀌는 것을 실제 앱에서 확인했다(2026-10-23)
- [x] 메뉴 막대, 키보드 단축키 — UI 4단계
- [x] 화면별 다듬기 (로딩·빈 화면, 알림, 히스토리·충돌 화면) — UI 5단계
- [x] 접근성 점검 — UI 6단계 (실제 VoiceOver·NVDA 확인은 남음)
- [x] 대형 저장소 성능 점검 (SPEC 성공 기준). 아래 측정은 macOS(Apple Silicon, SSD), git 2.54, 릴리스 빌드 엔진 기준
  - 파일 10만 개(변경 1천 개 + 추적하지 않는 파일 1만 개): `git status` 약 145ms, 파일 1만 1천 개 첫 렌더 약 100ms(jsdom, 가상 스크롤)라 1초 기준 안에 든다. 파일 감시기가 시작할 때 모든 파일을 훑던 파일 ID 캐시를 껐다. 파일 10만 개를 추가한 커밋을 선택하면 창이 멈추던 문제(커밋 상세의 파일 목록을 전부 그림)를 가상 스크롤로 고쳤다
  - 커밋 50만 개: commit-graph 파일이 없으면 `--topo-order`가 페이지마다 약 1.5~2초였다. 저장소를 열 때 없으면 한 번 만들도록 했고(약 2.4초, 백그라운드), 만든 뒤에는 첫 페이지 약 20ms, 25만 번째 커밋 근처 약 100ms, 마지막 페이지 약 190ms. 기록 마커(ref, 푸시 안 한 커밋, 들어올 커밋)는 약 35ms
  - 검색: 메시지 검색은 일치하는 게 없으면 전체를 훑어 약 1.7초, 코드 내용 검색(`-S`)은 약 22초, 경로 필터는 첫 페이지 약 3.5초. 검색어나 필터를 바꾸면 이전 git 프로세스를 취소한다(300ms 안에 끝남)
  - **남은 것**: 실제 앱(웹뷰)에서 끝까지 걸리는 시간은 직접 재지 않았다. Windows·Linux 측정

### 태그 관리 (v0.2)

기존에는 기록 배지와 커밋 메뉴에서만 태그를 다뤘고, Garam에서 만든 태그만 다음 푸시에 보낼 수 있었다. 이제 태그 목록에서 원격 상태를 확인하고, 터미널에서 만든 태그도 푸시하거나 지울 수 있다.

**실험으로 확인한 것**

- `git ls-remote --tags --refs <원격>`은 원격 태그마다 태그 객체 id를 준다. 로컬 `for-each-ref`의 `%(objectname)`과 비교하면 **원격과 같음 / 원격과 다름 / 원격에 없음**이 정확히 갈린다(annotated 태그는 다시 만들면 객체 id가 바뀌므로 같은 커밋이어도 "다름"이 된다)
- `fetch --prune`은 원격에서 지운 태그를 로컬에 남긴다. `--prune-tags`는 지우지만 한 번도 푸시하지 않은 로컬 태그까지 지우므로 쓰지 않는다. 그래서 "원격에 없음"은 아직 보내지 않은 태그일 수도, 원격에서 지운 태그일 수도 있다. Garam의 "아직 푸시하지 않은 태그" 목록에 있으면 앞쪽으로 확실히 안다
- 정렬: `--sort=-v:refname`은 `v1.10.0 > v1.9.0 > v1.2.0`처럼 버전 순서를 맞추고, 버전이 아닌 이름은 뒤로 간다. 다만 그대로는 `v0.1.0-rc.2`를 `v0.1.0`보다 새 버전으로 본다. `-c versionsort.suffix=-`를 주면 `-` 접미사를 정식 버전 전의 버전으로 봐서 `v0.1.0 > v0.1.0-rc.10 > v0.1.0-rc.2`가 된다(SemVer와 같음). `--sort=-creatordate`는 annotated면 태그를 단 날짜, lightweight면 커밋 날짜다

**화면**: 태그는 "기록 속 한 지점에 붙인 이름"이므로 기록 탭 안에서 다룬다. 태그를 쓰지 않는 사람에게는 아무것도 늘지 않고, 매일 쓰는 브랜치 선택기에 가끔 쓰는 태그를 섞지 않는다. GitHub Desktop은 태그 목록이 없고, Fork·Tower·GitKraken은 왼쪽 사이드바에 두는데 Garam에는 그런 사이드바가 없다.

- [x] 기록에서 태그가 달린 커밋의 오른쪽 클릭 메뉴에 태그마다 "v1 원격에 푸시"(원격과 같지 않을 때)·"v1 원격에 덮어쓰기…"(다를 때, 확인 대화상자)를 "v1 태그 삭제…" 곁에 둔다(히스토리 고도화 3번의 남은 것). 배지만의 메뉴는 두지 않았다: 배지가 커밋 행 안에 있어 행의 메뉴와 겹친다
- [x] 원격 상태 표시: 원격에 없거나 다른 태그의 배지에 작은 아이콘을 붙이고, 툴팁으로 "원격에 없음"·"원격과 다름"을 알린다. 같으면 표시하지 않는다
- [x] 기록 검색창 옆(브랜치 비교 버튼 곁)에 "태그" 버튼. 누르면 검색할 수 있는 태그 목록 팝오버: 이름, annotated면 메시지 첫 줄, 날짜, 원격 상태. 정렬은 "버전순 / 최신순"(기본 버전순). 고르면 그 태그부터의 기록을 보여 준다(범위 필터를 그 태그로 바꾸고 첫 행 선택). 행의 오른쪽 클릭은 배지와 같은 메뉴. 태그가 없으면 버튼을 숨긴다

### Pull Request 연동 (v0.2)

Garam에서 바로 PR을 만들고, 브랜치가 어떤 PR과 이어져 있는지 본다. GitHub 계정 로그인(Device Flow, 키체인 토큰) 위에 얹는다. 호스팅 계층을 나눠 두어 v0.3의 GitLab Merge Request로 같은 화면을 잇는다.

v0.2에서는 **PR 만들기와 상태 배지**까지 한다. PR 체크아웃은 후보로 남긴다(아래 "제외").

**실험으로 확인한 것** (2026-10-23. gh CLI의 토큰으로 했다. Garam 토큰과 같은 OAuth App 사용자 토큰(`gho_`)이고, scope는 `repo workflow read:org gist`다. PR이 실제로 만들어지는 요청은 보내지 않았다)

- **지금 scope(`repo workflow read:org user:email`)로 PR을 만들 수 있다. scope를 넓히거나 다시 로그인할 필요가 없다.** 존재하지 않는 head로 `POST /repos/{owner}/{repo}/pulls`를 보내면 공개 저장소와 비공개 저장소 모두 권한 검사를 통과해 422 `{"field":"head","code":"invalid"}`가 온다. GraphQL은 `X-Accepted-OAuth-Scopes: repo`이고 역시 통과한다. 토큰 없이 비공개 저장소를 조회하면 403이 아니라 404가 오므로, 404는 "저장소가 없음"과 "볼 권한이 없음"을 함께 뜻한다
- 만들기의 422 모양: head가 원격에 없으면 `field: head, code: invalid`, base가 없으면 `field: base, code: invalid`, 차이가 없으면 `code: custom, message: "No commits between main and main"`. 같은 head의 열린 PR이 이미 있을 때의 `custom` "A pull request already exists…"는 문서로만 확인했다(실험하려면 PR을 만들어야 한다). 메시지 문장은 바뀔 수 있으므로 Garam은 `field`·`code`로 나누고, 이미 있는 PR과 차이 없음은 만들기 전에 직접 확인해 막는다
- **CI 상태는 REST의 combined status(`/commits/{ref}/status`)로 보면 안 된다.** 상태가 하나도 없어도 `state: pending, total_count: 0`을 준다. GitHub Actions는 status가 아니라 check run을 남기므로, Actions만 쓰는 저장소는 늘 "진행 중"으로 보이게 된다. GraphQL `statusCheckRollup`은 check run과 status를 합친 하나의 상태이고, 아무것도 없으면 `null`이다(같은 커밋에서 확인)
- GraphQL 한 번(비용 1점, 시간당 5000점)으로 열린 PR 목록의 번호·초안 여부·head 브랜치·head 소유자·`reviewDecision`·마지막 커밋의 `statusCheckRollup`을 모두 받는다. `pullRequests(headRefName:)`는 소유자를 거르지 않아 포크의 같은 이름 브랜치도 섞이므로 `headRepositoryOwner`로 다시 거른다. `reviewDecision`은 `APPROVED`·`CHANGES_REQUESTED`·`REVIEW_REQUIRED`이고, 필수 리뷰 규칙이 없으면 `null`이다(문서)
- REST에 `If-None-Match`(ETag)를 붙이면 바뀌지 않았을 때 304가 오고 rate limit을 쓰지 않는다(core 사용량 12→12). GraphQL에는 조건부 요청이 없다
- 포크: GraphQL `isFork`, `parent { nameWithOwner defaultBranchRef }`로 PR을 보낼 상위 저장소와 기본 기준 브랜치를 얻는다. 포크에서 상위 저장소로 보낼 때 head는 `포크소유자:브랜치`다
- 문서로만 확인한 것: 조직이 OAuth App 접근 제한을 켜 두었으면 그 조직 저장소에 Garam 토큰이 통하지 않는다(403, 메시지에 "OAuth App access restrictions"). SAML SSO 조직은 토큰을 그 조직에 승인해야 하며 403에 `X-GitHub-SSO` 헤더(승인 URL)가 붙는다. GitHub Free의 비공개 저장소는 초안 PR을 만들 수 없다(422)

- 앱에서 확인한 것(2026-10-23): 조직 비공개 저장소에서 gh CLI 토큰(같은 계정)으로는 저장소가 보이고 푸시 권한도 있는데, Garam 토큰으로는 GraphQL이 `NOT_FOUND`("Could not resolve to a Repository")를 줬다. SSO 헤더는 없었다. 조직의 OAuth App 접근 제한으로 보이며, GraphQL은 이 경우 원인을 숨긴다. 그래서 `repository`가 `NOT_FOUND`면 REST `GET /repos/{owner}/{name}`에 다시 물어 접근 제한(403 메시지)이나 SSO(`X-GitHub-SSO`)를 가린다. 앱에서 REST가 실제로 접근 제한 메시지(403)를 주는 것을 확인했다. REST가 404만 주는 경우에 대비해 `github_not_found` 문구에도 조직 승인 가능성을 적고 "GitHub의 Garam 설정 열기" 버튼을 붙인다. 조직이 승인하면 바로 풀리므로 막힌 결과(`blocked`)는 캐시하지 않고 열 때마다 다시 묻고, 대화상자에 "다시 확인"을 둔다

**언제 보이나**

- PR 대상 저장소의 원격(현재 브랜치 업스트림의 원격, 없으면 기본 원격)이 github.com일 때만. 아니면 PR 메뉴와 배지를 모두 숨긴다
- 저장소에 Garam 계정이 연결돼 있어야 API를 부를 수 있다. 계정이 없으면 배지는 보이지 않고(묻지 않는다), "PR 만들기…"를 누르면 "이 저장소의 계정과 작성자" 대화상자로(로그인한 계정이 없으면 로그인으로) 이끈다
- SSH 원격도 계정을 고를 수 있다. 푸시는 지금처럼 SSH 키로 하고 계정은 GitHub API에만 쓴다. "이 저장소의 계정과 작성자"의 SSH 안내 문구를 그에 맞게 바꾼다

### 상황 알려 주기 (v0.2)

지금 무슨 일이 일어나는지, 무엇을 하면 무엇이 일어날지를 일이 생기기 전에 알린다. 브랜치가 기준에서 오래 갈라지면 충돌이 커지고, 풀·병합은 눌러 봐야 충돌을 알며, 병합된 브랜치는 쌓이기만 하고, 오류는 무엇을 하라는지 말하지 않는다.

**실험으로 확인한 것** (2026-10-23, git 2.54)

- `git merge-tree --write-tree A B`는 작업 폴더와 index를 건드리지 않고 병합 결과 트리를 만든다. 충돌이 있으면 종료 코드 1과 함께 충돌한 파일을 단계별(`<mode> <oid> <stage>\t<path>`)로 알린다. `--write-tree`는 **git 2.38**부터다. Garam이 지원하는 최소 버전은 2.35이므로, 2.38 아래에서는 git이 사용법 오류(129)를 내고 미리 보기 없이 커밋 수만 보인다. `--name-only`가 들어온 버전은 확인하지 못해 단계별 출력을 읽는다
- 리베이스를 미리 해 보는 `git replay`는 git 2.54에서 **브랜치를 직접 옮긴다**(`--ref-action=print`를 줘야 출력만 한다). 버전마다 동작이 다르고 실험 단계(EXPERIMENTAL)이며 충돌한 파일을 알려 주지 않는다. 그래서 리베이스 전 미리 보기도 병합 결과로 어림한다. 리베이스는 커밋을 하나씩 다시 얹으므로 중간 커밋에서 충돌이 더 날 수 있어 "충돌할 수 있는 파일"이라고 쓴다
- 원격에서 지운 브랜치는 `%(upstream:track)`이 `[gone]`이다(가져오기 `--prune` 뒤). 지금도 브랜치 목록이 "원격에서 삭제됨"으로 보인다
- GitHub의 squash 병합으로 들어간 브랜치는 `git branch --merged main`에 나오지 않는다(커밋이 다르다). 그 브랜치를 main에 병합한 결과 트리(`merge-tree`)가 main의 트리와 같으면 변경이 이미 main에 있다는 뜻이라 이것으로 가린다(squash 뒤 main에서 같은 줄을 다시 고쳤으면 못 가린다)
- 기준 브랜치를 얼마나 뒤처졌는지는 `rev-list --count HEAD..origin/main`. 원격 추적 브랜치는 백그라운드 가져오기(5분)가 새로 고친다. 가져오기가 끝났다는 이벤트는 없지만 모든 동기화 뒤에 변경 사항 쿼리를 무효화하므로, 같은 키 아래 두면 저절로 다시 계산된다

**공통 엔진**

- [x] `branch::merge_preview(repo, theirs)` → `MergePreview { commits, conflicts: Option<Vec<String>> }`: 가져올 커밋 수(`rev-list --count HEAD..theirs`)와 충돌할 파일(`merge-tree --write-tree -z --name-only --no-messages`, 종료 코드 0·1이 아니면 `None`). `branch::commits_to_merge`를 대신한다
- [x] 측정: `merge-tree` 시간은 커밋 수보다 트리 크기를 따른다. 파일 5만 개, 충돌 파일 21개에서 35ms, Garam 저장소에서 10ms(macOS). 브랜치 정리는 `--merged`에 없는 브랜치마다 한 번씩 돌린다

**1. 기준 브랜치가 앞서 갔다는 알림**

- [x] 이름: 버튼과 대화상자는 "main 내용 반영하기"다. 처음 설계는 "main 내용 가져오기"였지만, GLOSSARY에서 "가져오기"는 fetch이고 툴바에 "origin에서 가져오기"가 있어 같은 낱말이 다른 동작을 뜻하게 되어 바꿨다
- [x] 기준은 원격의 기본 브랜치(`refs/remotes/origin/HEAD`가 가리키는 `origin/main`, PR 제안과 같은 값)다. 현재 브랜치가 기본 브랜치이거나, 브랜치가 아니거나(분리된 HEAD), git이 기본 브랜치를 모르면 알리지 않는다(기본 브랜치에서는 지금처럼 툴바의 받을 커밋 수가 알린다)
- [x] 알림 자리: 변경 사항 탭 위의 배너(자동 보관·충돌 배너와 같은 모양). "main에 새 커밋 12개가 있습니다"와 충돌 미리 보기("지금 반영하면 파일 1개가 충돌합니다. 오래 갈라질수록 충돌이 커지니 일찍 반영하세요"), 버튼 "main 내용 반영하기…"·"나중에"
- [x] 언제 보이나: main이 바뀔 때마다 띄우면 배너를 무시하게 된다. 그래서 **충돌이 예상되거나 받을 커밋이 10개 이상일 때만** 띄운다. "나중에"는 그 상태를 기억해 두고, 충돌할 파일이 새로 생기거나(없다가 생긴 것 포함) 받을 커밋이 다시 10개 더 쌓이면 다시 띄운다(저장소별, 창 안에서만)
- [x] "main 내용 반영하기" 대화상자: 열 때 묻지 않는 가져오기를 한 번 하고(PR 대화상자와 같다), 가져올 커밋 수와 충돌할 파일 목록을 보인다. 방식은 **병합**(기본)과 **리베이스**. 리베이스는 원격에 올리지 않은 브랜치(업스트림이 없거나 원격에서 지워진 브랜치)에서만 고를 수 있다. 이미 푸시한 브랜치를 리베이스하면 강제 푸시가 필요한데 Garam에는 강제 푸시가 없고, 함께 쓰는 사람의 기록을 바꾸기 때문이다(그때는 "이미 푸시한 브랜치는 병합으로 반영합니다"를 보인다)
- [x] 커밋하지 않은 변경 사항이 있으면 `--autostash`로 잠시 보관했다가 다시 꺼낸다고 대화상자에 쓴다(풀의 "변경 사항을 잠시 보관하고 풀하기"와 같은 방식, `merge`·`rebase` 모두 지원). 충돌하면 기존 충돌 배너와 해결 화면으로 이어진다(리베이스 계속·건너뛰기·중단은 M7에 있다)
- [x] 엔진: `branch::base_status(repo)` → `{ base, behind, conflicts }`(위 `merge::preview` 재사용), `branch::update_from(repo, base, Rebase|Merge)`(`merge --no-edit --autostash` / `rebase --autostash`)

**2. 실행 전에 결과 미리 보기**

- [x] 병합 대화상자(현재 브랜치에 병합): 커밋 수 아래에 충돌할 파일 목록. 충돌이 예상되면 버튼은 "병합하고 충돌 해결하기"로 이름이 바뀐다(막지는 않는다)
- [x] 풀: 받을 커밋이 있을 때 마지막 가져오기 기준으로 업스트림과의 충돌을 미리 계산해 둔다. 충돌이 예상될 때만 풀 버튼을 누르면 확인 대화상자("풀하면 파일 2개가 충돌합니다 · 그래도 풀하기 / 취소")를 띄운다. 충돌이 없으면 지금처럼 바로 풀한다(확인 단계를 늘리지 않는다). 풀은 다시 가져오므로 그 사이 원격이 바뀌면 예측과 다를 수 있다. 풀 버튼 툴팁에 "커밋 3개를 받습니다 · 파일 1개 충돌 예상". 풀 확인 대화상자는 늘 "충돌할 수 있는 파일"로 쓴다(풀은 다시 가져오므로 그 사이 원격이 바뀔 수 있다)
- [x] 리베이스로 풀하는 설정(`pull.rebase`)이어도 같은 문구다(위와 같이 풀 확인은 늘 어림으로 쓰므로 설정을 따로 읽지 않았다)

**3. 브랜치 정리**

- [x] 후보: 현재 브랜치와 기본 브랜치를 뺀 로컬 브랜치 중 (가) 기본 브랜치(`origin/main`)에 병합된 것(`--merged`, 또는 squash 병합으로 변경이 이미 들어간 것), (나) 업스트림이 원격에서 지워진 것. 둘 다면 병합된 것으로 본다. 만들고 아직 커밋하지 않은 브랜치(reflog에 만든 기록 하나뿐)도 기본 브랜치의 조상이라 병합된 것처럼 보이므로 뺀다(방금 만든 브랜치를 지우자고 하면 안 된다)
- [x] 자리: 브랜치 메뉴 "브랜치 정리…"(새 브랜치·이름 바꾸기 아래), 브랜치 목록 아래에 "정리할 브랜치 n개…"(후보가 있을 때만, 목록을 연 동안만 계산)
- [x] 대화상자: 후보마다 체크박스, 이름, 이유("main에 병합됨"·"원격에서 삭제됨")와 마지막 커밋 시각. 병합되지 않았는데 원격에서만 지워진 브랜치는 "main에 없는 커밋 3개"를 붙이고 **기본으로 체크하지 않는다**(다른 곳에 없는 커밋을 잃을 수 있다). 버튼 "브랜치 n개 삭제"(위험 버튼)
- [x] 삭제는 `branch -D`(squash 병합된 브랜치는 `-d`가 거부하므로, 병합 여부는 Garam이 위에서 확인한다). 원격 브랜치는 지우지 않는다
- [x] 지운 뒤 알림 "브랜치 4개를 삭제했습니다 · 되돌리기": 지우기 전 커밋 id와 업스트림 설정을 기억해 두었다가 다시 만든다(업스트림이 원격에 아직 있으면 다시 연결). 스태시 버리기의 되돌리기와 같은 방식. 되돌리기는 대화상자가 닫힌 뒤에 누르므로 `mutate`의 호출별 콜백 대신 `mutateAsync`의 결과로 알린다(react-query는 컴포넌트가 사라지면 호출별 콜백을 부르지 않는다)
- [x] 엔진: `branch::cleanup_candidates(repo, base)`, `branch::delete_many(repo, names)` → 되살리기용 `{ name, oid, upstream }`, `branch::restore(repo, deleted)`

**4. 오류 안내에 해결 버튼**

- [x] 오류 알림(오른쪽 아래)도 정보 알림처럼 동작 버튼 하나를 받는다(`showErrorWithAction(error, action)`. `showError`는 `onError`에 그대로 넘길 수 있게 인자 하나로 둔다). 대화상자 안의 `ErrorMessage`도 같은 `action`을 받는다. 풀이 보관한 변경을 다시 꺼내다 충돌했다는 정보 알림에도 "충돌 해결하기"를 붙였다
- [x] 무엇이 실패했는지에 따라 할 일이 정해지는 경우에만 붙인다(오류 종류만으로 정하지 않고, 실패한 곳이 고른다):
  - 푸시가 non-fast-forward로 거부됨 → "먼저 풀하기"(풀한 뒤 다시 푸시하지는 않는다. 풀에서 충돌할 수 있으므로 사용자가 결과를 보고 푸시한다)

  - 병합·전환이 커밋하지 않은 변경 사항 때문에 멈춤 → "변경 사항을 잠시 보관하고 다시 하기"(`--autostash`, 풀은 이미 대화상자로 묻는다)
- [x] `pull.ff=only`에서 갈라진 브랜치(`cannot_fast_forward`)는 사용자가 고른 설정이므로 버튼 없이 이유만 보인다

- [x] 먼저 끼어드는 두 가지만 끌 수 있다. 하는 일이 달라 하나로 묶지 않는다(배너는 끄고 풀 전 확인은 켜 둘 수 있다)
  - "기준 브랜치가 앞서 가면 알리기"(기본 켬): 1번의 배너

### 커밋 전 안전 검사 (v0.2)

커밋하면 안 되는 것이 커밋에 들어가려 할 때 커밋 버튼을 누른 순간 알린다. 셋 다 처음 쓰는 사람이 혼자서는 되돌리기 어려운 실수다. 비밀 값은 푸시하면 지워도 이미 늦고(키를 바꿔야 한다), 큰 파일은 한 번 커밋하면 지워도 기록에 남아 저장소가 계속 무겁고, `node_modules`는 한 번 들어가면 빼는 법(`git rm --cached`)을 알아야 한다.

**실험으로 확인한 것** (2026-10-23, git 2.54)

- 커밋에 들어갈 것은 index와 HEAD의 차이다. Garam의 "커밋에 포함"은 곧 스테이징이므로(줄 단위 포함도 index에 기록된다) 검사도 index만 보면 된다. `git diff --cached --raw -z`가 파일마다 상태와 새 blob id를 주고, 그 id들을 `git cat-file --batch-check`에 한 번에 넘기면 크기가 나온다(작업 폴더를 읽지 않으므로 커밋될 내용 그대로의 크기다)
- 더해지는 줄은 `git diff --cached -U0 --no-ext-diff --no-textconv`의 `+` 줄이다. 바이너리 파일은 "Binary files … differ"로만 나오므로 내용 검사에서 저절로 빠진다. 이름 바꾸기는 기본 이름 바꾸기 감지로 바뀐 줄만 나온다(옮기기만 한 파일을 다시 경고하지 않는다)
- 많은 사용자가 전역 ignore(`core.excludesFile`)에 `.DS_Store`를 넣어 두어 `git add -A`에도 들어오지 않는다. 그래서 무시할 파일 제안은 실제로 index에 들어간 것만 본다
- GitHub은 50MiB가 넘는 파일을 푸시하면 경고하고, 100MiB가 넘으면 거부한다(문서). Git LFS 포인터 파일은 몇백 바이트라 크기 검사에 걸리지 않는다

**언제 검사하나**

- 커밋 버튼(⌘↩ 포함)을 누르면 `git commit` 전에 검사한다. 걸린 것이 없으면 지금처럼 바로 커밋한다. 마지막 커밋 수정(amend)도 같은 검사를 한다(이미 HEAD에 있는 내용은 그때 검사했으므로 index와 HEAD의 차이만 본다)
- 파일 목록에 미리 표시하지는 않는다. 내용 검사를 파일 감시가 새로 고칠 때마다 돌리면 비싸고, 커밋 직전 한 번이면 실수를 막기에 충분하다
- "다시 묻지 않기"는 두지 않는다. 더해지는 줄·바뀐 blob·새로 더한 파일만 보므로, 일부러 넣은 테스트용 키도 그 줄을 더하는 커밋에서 한 번만 걸린다. 검사를 아예 끄는 설정은 설정 > 일반에 "커밋 전 안전 검사"(기본 켬)로 둔다. 설정 > Git은 git 전역 설정에 저장되는 값만 모은 곳이라 앱 설정을 섞지 않았다

**무엇을 찾나**

- [x] 비밀 값(위험): 이름으로 `.env`·`.env.*`(`.example`·`.sample`·`.template`으로 끝나면 제외), 개인 키 파일(`id_rsa`·`id_dsa`·`id_ecdsa`·`id_ed25519`, `*.pem`·`*.key`·`*.p12`·`*.pfx`), 내용으로 더해지는 줄의 개인 키 머리말(`-----BEGIN … PRIVATE KEY-----`)과 형태가 분명한 토큰(GitHub `ghp_`·`gho_`·`ghu_`·`ghs_`·`ghr_`·`github_pat_`, AWS 액세스 키 `AKIA…`, Slack `xox?-`, Stripe `sk_live_`·`rk_live_`, Google API `AIza…`, Anthropic `sk-ant-`, OpenAI `sk-proj-`). 접두사와 길이·글자 종류가 모두 맞을 때만 걸어 오탐을 줄인다. - [x] 큰 파일(주의): 커밋될 blob이 50MiB 이상. 100MiB 이상이면 "GitHub은 푸시를 거부합니다"라고 분명히 말한다. Git LFS를 소개하는 링크를 붙인다(LFS 설정 자체는 v0.3 후보 "Git LFS 자동 감지와 설정 안내")

### 히스토리 고도화 (v0.2 후보)

M6의 커밋 목록을 "지금 내 브랜치가 원격과 어떤 관계인지"까지 읽히는 화면으로 만든다. 비용이 작고 체감이 큰 것부터 한다. 한국어 UI에서는 "기록"이라고 부른다(GLOSSARY).

1. 위치 표시
   - [x] ref 배지: 커밋 옆에 로컬 브랜치·원격 브랜치·태그·분리된 HEAD. 같은 커밋을 가리키는 로컬·원격 브랜치는 배지 하나로 합친다. 현재 브랜치는 굵게
   - [x] 아직 푸시하지 않은 커밋 표시(업스트림이 있으면 `HEAD ^@{u}`, 없으면 `HEAD --not --remotes`, 원격이 없으면 표시 안 함)
   - [x] 아직 가져오지 않은 커밋(`@{u} ^HEAD`)을 목록 맨 위에 흐리게 표시. fetch 뒤 ahead/behind 숫자를 눈으로 확인한다
2. 검색과 필터
   - [x] 메시지·작성자·해시 검색(`--grep`, `--author`, 대소문자 무시·글자 그대로). git은 `--author`와 `--grep`을 AND로 묶으므로 검색 대상(메시지/작성자/코드)을 고른다. 메시지 검색에 16진수 7자 이상을 넣으면 그 커밋도 맨 위에 보여준다
   - [x] 코드 내용 검색(pickaxe `-S`)
   - [x] 경로 필터, 범위 선택(현재 브랜치 / 모든 브랜치와 태그 / 특정 브랜치), `--first-parent` 보기
   - [x] 검색창(⌘F / Ctrl+F, 입력이 300ms 멈추면 검색), 필터 팝오버, 결과가 없을 때 지우기 버튼. 필터는 저장소별로 탭을 오가도 유지한다
   - **남은 확인**: 대형 저장소에서 코드 내용 검색은 느리다(커밋 50만 개에서 약 22초). 새 검색을 시작하면 이전 git 프로세스는 취소한다(M8 성능 점검)
3. 커밋 동작
   - [x] 체리픽(메뉴). HEAD에서 이어진 목록에서는 이미 들어 있는 커밋이라 메뉴를 숨기고, 아직 풀하지 않은 커밋과 다른 범위에서만 보인다. 충돌하면 기존 충돌 배너로 이어지고, 바뀌는 게 없는 체리픽은 git이 진행 중으로 남기므로 중단하고 알린다
   - [x] 다른 브랜치로 체리픽(메뉴, 여러 커밋도): 대상 로컬 브랜치로 전환한 뒤 적용하고 그 브랜치에 남는다(GitHub Desktop과 같은 흐름). 작업 폴더가 깨끗해야 하고, 충돌하면 대상 브랜치에서 충돌 배너로 이어진다
   - [x] 체리픽을 브랜치로 끌어 놓기: 커밋 행(여러 개 선택했으면 모두)을 끌어 툴바 브랜치 버튼 위에 잠시 두면 브랜치 목록이 열리고, 로컬 브랜치에 놓으면 체리픽한다(현재 브랜치면 그대로, 다른 브랜치면 전환 후). 커서를 따라가는 표시와 브랜치 행·툴바 버튼의 강조로 어디에 놓일지 알려 주고(끌기가 다른 곳에서 시작되면 `:hover`가 따라오지 않는 웹뷰가 있어 끌기 상태로 직접 칠함) Esc로 취소한다. 창의 파일 드롭이 HTML 끌어 놓기를 가로채는 OS가 있어 포인터 이벤트로 직접 구현했다
   - [x] 끌어서 커밋 순서 바꾸기: 기록 목록 안에서 커밋(여러 개도)을 행 사이로 끌면 놓일 자리에 선이 보이고, 놓으면 그 순서로 다시 쌓는다. 현재 브랜치 줄의 최근 커밋에서 옮긴 가장 깊은 곳까지만 interactive rebase(`GIT_SEQUENCE_EDITOR`로 미리 만든 todo를 넣음)로 다시 쓴다. 병합 커밋이 섞이면 안 되고 작업 폴더가 깨끗해야 한다. 충돌하면 rebase 충돌 배너로 이어지고, 푸시한 커밋이 섞이면 강제 푸시 경고 대화상자를 거친다
   - [x] 커밋을 다른 커밋에 끌어 놓아 합치기: 행 가운데는 합치기, 위·아래 가장자리는 기존 순서 변경으로 구별한다. 여러 개·떨어진 커밋도 대상에 합치고 사이의 커밋은 별도로 남긴다. 메시지·대상 목록 확인과 푸시한 기록 경고를 거치며 대상 작성자를 유지한다. HEAD·브랜치 변경, 진행 중인 작업, 추적 중인 미커밋 변경, 병합 커밋을 검사하고, 충돌은 기존 리베이스 계속·중단 화면으로 이어진다. 자기 자신·함께 끄는 커밋 위, 검색·경로 필터·다른 브랜치 범위에서는 합치지 않는다
     - 실제 앱에서 확인함(2026-10-27, macOS 개발 빌드, 별도 시험 저장소): `Dragged`를 한 커밋 건너 `Target` 가운데에 놓아 합친 뒤 `Between`이 별도 커밋으로 남고 파일 내용이 유지됨을 확인했다. 영어·다크에서도 대상 목록·메시지·버튼을 확인하고 취소했으며, 행 위 가장자리에 놓으면 합치기 대신 순서가 바뀌는 것을 확인했다. 언어·테마는 기존 시스템 설정으로 복원했다. 여러 개 선택·자기 자신·취소·놓는 위치 재검사·푸시 경고는 화면 테스트로, 작성자·빈 커밋·첫 커밋·스테이지 보호·충돌 계속·중단은 실제 저장소 통합 테스트로 확인했다
   - [x] 이 커밋으로 리셋: 대화상자에서 스테이지 유지(soft) / 작업 폴더 유지(mixed) / 버리기(hard)를 고른다. hard는 위험 버튼과, 커밋하지 않은 변경 사항이 있으면 몇 개가 사라지는지 알린다
   - [x] 마지막 커밋 취소: HEAD이고 아직 푸시하지 않았을 때(원격이 없으면 언제나), 병합 커밋이 아닐 때만. 변경 사항은 스테이지된 채로 남고 메시지는 커밋 폼에 다시 채운다. 그사이 HEAD가 바뀌었으면 거부한다. 첫 커밋도 취소할 수 있다(태어나지 않은 브랜치로 돌아감)
   - [x] 이 커밋으로 전환(분리된 HEAD 안내, "여기서 브랜치 만들기"로 바꿀 수 있음), 여기에 태그 만들기(메시지를 쓰면 annotated). 태그 푸시는 v0.2 태그 관리에서
   - [x] 태그를 푸시와 함께 보내기: 앱에서 만든 태그는 저장소별 "아직 푸시하지 않은 태그" 목록(`.git/garam/unpushed-tags`, 워크트리끼리 공유)에 남고, 다음 푸시·게시가 브랜치와 함께 하나씩 이름을 지정해 보낸다(lightweight 태그도 가고, 가져온 태그나 터미널에서 만든 태그는 건드리지 않음). 보낼 커밋이 없어도 태그가 있으면 푸시 버튼이 켜지고 태그 수를 보여 준다. 원격에 같은 이름의 태그가 다른 커밋에 있으면 거부되고 목록에 남는다(`remote_tag_exists`). 가져온 태그도 로컬 `refs/tags`에 섞이므로, 원격에 묻지 않고 어느 태그가 원격에 없는지 알 방법이 없어 목록으로 기억한다
   - [x] 태그 삭제: 커밋 오른쪽 클릭 "v1 태그 삭제…"(확인 대화상자). 푸시한 적이 있을 수 있는 태그는 "origin에서도 삭제"를 고를 수 있다(기본은 끔, 원격을 먼저 지우고 로컬을 지움). 남겨 두면 다음 가져오기에서 다시 생길 수 있다고 알린다. 원격에 이미 없는 태그는 삭제된 것으로 친다
   - **완료**: 터미널에서 만든 태그 푸시와 태그 목록 화면은 위 "태그 관리"에서 구현·확인했다.
4. 커밋 그래프
   - [x] 레인 계산과 그리기. git은 `--topo-order`로 자식을 부모보다 먼저 주고, 레인은 프론트(`features/history/graph.ts`)가 불러온 행 전체로 계산한다. 페이지가 늘어도 같은 함수로 이어지므로 페이지 사이 상태를 따로 넘기지 않는다. 레인은 옆으로 밀리지 않고, 10개를 넘으면 잘린다. 그래프 칸 너비는 행마다 그 행이 쓰는 레인만큼이라, 나중에 불러온 넓은 구간 때문에 위쪽 행에 빈 여백이 생기지 않는다

### GitHub 계정 로그인 (v0.2 후보)

버튼 하나로 브라우저에서 GitHub에 로그인하고, 여러 계정을 등록해 저장소마다 골라 쓴다. 계정 로그인을 추가하기 전에는 HTTPS 원격에서 개인 액세스 토큰을 직접 붙여 넣어야 했다(M5의 자격 증명 대화상자).

- [x] 저장소별 계정 선택: 커밋 영역의 작성자 줄 → "이 저장소의 계정과 작성자". 원격 URL의 사용자 이름 → 소유자 → 작성자 이메일 순으로 추천하고, 선택은 저장소 목록(`repositories.json`)에 저장
- [x] 조직 멤버십으로 추천 (`read:org`, 원격 소유자가 조직일 때): 로그인할 때 `/user/orgs`로 소속 조직을 읽어 계정 정보에 저장한다. 추천 순서는 URL의 사용자 이름 → 소유자 → 소유 조직의 멤버(여럿이면 작성자 이메일로 고름) → 작성자 이메일. 조직을 읽지 못해도 로그인은 계속한다. 이 기능 전에 로그인한 계정은 다시 로그인해야 조직이 반영된다
- [x] 선택한 계정의 토큰을 git에 넘기기 (credential helper, ARCHITECTURE.md 2.10). fetch·pull·push·게시와 백그라운드 fetch에 적용
- [x] 계정과 작성자 연결: 저장소에 계정을 고르면 그 계정의 인증된 이메일(`/user/emails`)과 noreply 주소 중에서 작성자 이메일을 고르게 한다
- [x] 불일치 경고: 저장소에 연결한 계정과 작성자 이메일이 맞지 않으면 커밋 영역과 대화상자에 알린다(예: 개인 계정으로 push하는데 작성자가 회사 이메일). 커밋을 막지는 않는다
- [x] 복제할 때 계정 고르기: 로그인한 계정이 있으면 복제 대화상자에 "GitHub 계정"이 나오고, URL을 따라 추천 계정이 골라진다(직접 고르면 그대로 둔다). 고른 계정으로 HTTPS 복제에 로그인하고, 복제한 저장소에 그 계정을 저장한다. SSH URL이면 복제에는 SSH 키를 쓰고 계정은 PR에 쓴다고 안내한다. 복제한 저장소의 작성자 이메일(전역 설정이 아니라 `includeIf` 등을 거쳐 실제로 쓰이는 값)이 그 계정에 없으면, 복제가 끝난 뒤 같은 대화상자에서 작성자를 묻는다: 계정의 인증된 이메일·noreply 주소 중 하나를 저장소 설정(`--local`)에 저장하거나, 지금 작성자를 그대로 쓴다. 대화상자를 닫으면 그대로 쓴다
- [x] SSH 원격의 계정별 키 (`core.sshCommand`): 원격이 SSH인 저장소의 "이 저장소의 계정과 작성자"에 "SSH 키"가 나온다. `~/.ssh`의 키(`.pub`가 있는 것) 중 하나를 고르면 저장소 설정에 `ssh -i <키> -o IdentitiesOnly=yes`를 저장하고, "내 SSH 설정 사용"을 고르면 지운다. 사용자가 직접 쓴 명령은 "지금 명령 유지"로 보여 주고 건드리지 않는다. 공개 키 주석이 계정 이메일인 키를 추천한다. 키를 새로 만들거나 GitHub에 올리지는 않는다(`admin:public_key` scope가 필요)
- [x] GitHub Enterprise Server 호스트 지원: 설정 → 계정의 "GitHub Enterprise Server에 로그인"에서 서버 주소와 그 서버에서 만든 개인 액세스 토큰으로 로그인한다(Device Flow는 서버마다 OAuth App 등록이 필요해 쓰지 않는다). "토큰 만들기"가 필요한 scope를 채운 토큰 페이지를 연다. 푸시·풀의 자격 증명, 계정 추천, PR(REST `/api/v3`, GraphQL `/api/graphql`), 커밋·이슈 링크가 그 호스트에서 동작한다. 아바타는 CSP 때문에 첫 글자로 보인다. 실제 GHES 서버에서는 확인하지 못해(목 서버로만 테스트) 버튼과 대화상자에 "베타"를 붙이고, 문제가 있으면 이슈로 알려 달라고 안내한다. 데이터 레지던시를 쓰는 GitHub Enterprise Cloud(`*.ghe.com`, API가 `api.<이름>.ghe.com`)는 지원하지 않는다

**설계 메모**

- **Device Flow를 쓰는 이유**: 웹 플로(브라우저 → loopback 리디렉션)는 토큰 교환에 client secret이 필요한데, 오픈소스 앱에 넣으면 공개된다. Device Flow는 client ID만으로 동작하고 GitHub CLI도 이 방식을 쓴다. 사용자가 코드를 붙여 넣는 단계가 하나 더 있지만, 코드를 미리 클립보드에 넣어 두면 부담이 작다.
- **토큰 전달**: askpass보다 **credential helper**가 맞다. 사용자의 osxkeychain 같은 도우미에 다른 자격 증명이 저장돼 있으면 git이 askpass를 부르지 않기 때문이다. 네트워크 작업에 `-c credential.https://github.com.helper=`(목록 초기화)와 `-c credential.https://github.com.helper=<garam 실행 파일>`을 붙이고, askpass처럼 앱 실행 파일을 credential helper 모드로 실행해 작업 ID로 계정을 찾아 토큰을 돌려준다. 계정이 없는 저장소는 지금처럼 사용자 설정을 그대로 쓴다.
- **보안 원칙 변경**: ARCHITECTURE.md 7장의 "자격 증명은 앱이 저장하지 않는다"를 "앱이 발급받은 GitHub 토큰만 OS 키체인에 저장한다"로 바꿔야 한다. 토큰은 파일·로그·프론트로 보내지 않는다.
- **만료 토큰을 쓰지 않는다**: OAuth App의 "Expire user access tokens"는 끈다. 만료 토큰은 refresh token으로 갱신해야 하는데, 갱신 요청에 client secret이 필요해 Device Flow를 고른 이유가 사라진다. 대신 키체인 저장, 최소 scope, 로그아웃 시 폐기로 위험을 줄인다.
- **다른 credential helper와 함께 쓰기**: 사용자가 이미 `gh auth git-credential`이나 osxkeychain을 쓰고 원격 URL에 사용자 이름(`https://me@github.com/...`)을 넣어 계정을 구분할 수도 있다. 계정을 고르지 않은 저장소에서는 이 설정을 건드리지 않는다.
- **새 의존성**: HTTPS 클라이언트(`reqwest`, rustls)와 키체인 접근(`keyring`). 토큰을 GitHub에서 폐기하는 API(`DELETE /applications/{client_id}/token`)는 client secret이 필요해 앱이 직접 부를 수 없다. 그래서 로그아웃은 키체인에서 토큰을 지우고, 권한까지 취소하려는 사용자를 GitHub 설정 페이지로 안내한다.
- **테스트**: Device Flow와 API는 목 서버로, credential helper 프로토콜은 `git credential fill`로 통합 테스트한다.

### 커밋 다듬기 (v0.3 후보)

SPEC 7장의 인터랙티브 rebase 중 남은 것과 함께 한다.

- CI 호환성: amend·fixup의 특수 파일명 테스트는 Windows에서 허용하지 않는 `*`만 빼고 한글·공백·대괄호 검증을 유지한다. macOS·Linux에서는 `*`가 포함된 리터럴 경로도 계속 검증한다.

- [x] 직전 커밋 다시 편집(amend): 기록의 마지막 커밋 메뉴 "커밋 수정…" 또는 변경 사항의 "마지막 커밋 수정…"에서 편집 모드로 들어간다. 기존 커밋의 변경과 새 변경을 함께 보여 주고, 파일·줄을 포함하거나 제외하고 메시지를 고친다. 별도 인덱스를 사용하므로 취소 시 원래 커밋·스테이지·작업 폴더를 유지하고, 저장 시 제외한 내용은 작업 폴더에 남는다. 아직 푸시하지 않은 비병합 커밋만 지원하고, HEAD·브랜치·실제 스테이지 변경을 감지하면 저장을 거부한다. 공동 작성자 꼬리말·원래 작성자·서명·훅·안전 검사를 유지한다. 직전 커밋에는 fixup 메뉴 대신 amend를 제공한다
  - 실제 앱에서 확인함(2026-10-27, macOS 개발 빌드, 별도 시험 저장소, 한국어·라이트): 기록 메뉴에서 편집 모드로 들어가 기존 커밋의 줄과 파일을 제외하고 새 파일을 포함해 저장했다. 제외한 두 변경은 작업 폴더에 남고, 메시지와 선택 상태는 기록 탭을 오가도 유지된다
