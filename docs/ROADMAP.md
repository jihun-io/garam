# Garam 로드맵

> 각 마일스톤은 "동작하는 앱"으로 끝난다. 완료 조건을 모두 만족해야 다음 단계로 넘어간다.
> 마일스톤 순서는 의존 관계를 따른다. 진행하면서 체크박스를 갱신한다.

## M5. 원격 동기화

- [x] fetch/pull/push + 진행률 (pull은 fetch 단계만 취소 가능, 리베이스·ff-only 설정 존중)
- [x] ahead/behind 표시, publish (업스트림이 원격에서 삭제된 브랜치 포함)
- [x] askpass 헬퍼 + 앱 내 자격 증명 프롬프트 (HTTPS, SSH 암호, SSH 호스트 키 확인)
- [x] 백그라운드 fetch (5분, 프롬프트 없음 — 주기 설정은 M8)
- [x] non-fast-forward, 인증 실패 등 오류 안내
- [x] 커밋하지 않은 변경 사항 때문에 풀이 멈추면 "변경 사항을 잠시 보관하고 풀하기"를 제안(`--autostash`, 병합·리베이스 모두). 다시 꺼낼 때 충돌하면 보관한 내용은 스태시(autostash)에 남기고 충돌 배너로 이어진다. git은 병합할 때 스테이지된 변경 사항이 하나라도 있으면 겹치는 파일이 없어도 거부한다
- [x] 틀린 암호 안내: ssh는 키 암호를 같은 문구로 세 번까지 묻기 때문에, 한 작업에서 같은 프롬프트가 다시 오면 "입력한 암호가 맞지 않습니다"를 보여 준다. SSH 키 암호 창에는 자격 증명 도우미 안내 대신 "SSH 에이전트에 키를 추가해 두지 않으면 매번 묻는다"를 보여 준다(도우미는 HTTPS만 기억한다)
- [x] "이 컴퓨터에 기억": 모든 호스트에 쓰는 credential helper가 없을 때(Linux에서 흔함) 암호 입력 창에 체크박스(기본 켬)를 보여 주고, 인증에 성공한 값만 OS 키체인에 저장해 다음부터 묻지 않는다. 거부되면 저장한 값을 지운다. 설정 > 계정에서 기억한 로그인을 보고 지운다(ARCHITECTURE.md 2.7). helper가 있으면(macOS·Windows 기본) 지금처럼 그 helper에 맡기고 체크박스는 없다

**확인함**(2026-10-23, macOS 릴리스 빌드 rc.2, 로컬 시험 서버): SSH는 처음 보는 호스트 키 확인, 암호 걸린 키의 암호 입력, 다시 푸시할 때 암호만 묻기, 세 번 틀리면 인증 실패 안내까지. HTTP Basic 인증(사용자 이름 + 토큰)은 가져오기·푸시, 틀린 토큰, 취소까지. GitHub 계정 로그인(Device Flow)과 키체인 저장, 그 계정으로 푸시도 확인했다. "이 컴퓨터에 기억"은 개발 빌드에서 helper를 비운 저장소로 확인했다.

**확인함**(2026-10-23, Windows 11 ARM의 UTM 가상 머신, 릴리스 워크플로를 손으로 실행해 만든 x64 NSIS 빌드, Mac에 띄운 시험 서버): GUI 서브시스템 실행 파일이 askpass와 credential helper로 실행될 때 답을 git에 제대로 넘긴다. HTTP 토큰 로그인과 "이 컴퓨터에 기억"(Windows 자격 증명 관리자), SSH 키 암호와 처음 보는 호스트 키 확인 모두 동작했다. Git for Windows는 Git Credential Manager를 기본으로 켜 두므로, Garam 창이 뜨려면 저장소에서 `credential.helper`를 비워야 했다(GCM이 있으면 GCM이 로그인을 맡는다)

**남은 확인**: Linux에서의 로그인(대개 helper가 없어 "이 컴퓨터에 기억"이 실제로 쓰이는 환경, Secret Service가 없을 때 키체인 저장이 실패하면 어떻게 보이는지 포함).

## M8. 마무리와 첫 릴리스 (v0.1.0)

**v0.1.0 공개**(2026-10-23): `v0.1.0` 태그의 릴리스 워크플로가 세 OS 모두 성공했고, 초안을 공개해 GitHub의 최신 릴리스가 되었다. 올라간 파일은 macOS 유니버설 DMG와 업데이트용 `.app.tar.gz`, Windows NSIS 설치 파일, Linux AppImage·deb, 각각의 `.sig`, `latest.json`이다(MSI 없음). 업데이트 피드(`releases/latest/download/latest.json`)가 `0.1.0`과 세 OS 항목으로 응답한다.

UI 개선은 `docs/UI.md` 계획(1~6단계)을 따른다.

- [x] 설정 화면 (언어, 테마, Git 사용자 정보, 에디터·터미널, fetch 주기) — UI 3단계
  - 언어를 바꾸고 다시 시작하면 macOS가 직접 넣는 메뉴 항목까지 그 언어로 바뀌는 것을 실제 앱에서 확인했다(2026-10-23)
- [x] 메뉴 막대, 키보드 단축키 — UI 4단계
- [x] 화면별 다듬기 (로딩·빈 화면, 알림, 히스토리·충돌 화면) — UI 5단계
- [x] 접근성 점검 — UI 6단계 (실제 VoiceOver·NVDA 확인은 남음)
- [x] 대형 저장소 성능 점검 (SPEC 성공 기준). 아래 측정은 macOS(Apple Silicon, SSD), git 2.54, 릴리스 빌드 엔진 기준
  - 파일 10만 개(변경 1천 개 + 추적하지 않는 파일 1만 개): `git status` 약 145ms, 파일 1만 1천 개 첫 렌더 약 100ms(jsdom, 가상 스크롤)라 1초 기준 안에 든다. 파일 감시기가 시작할 때 모든 파일을 훑던 파일 ID 캐시를 껐다. 파일 10만 개를 추가한 커밋을 선택하면 창이 멈추던 문제(커밋 상세의 파일 목록을 전부 그림)를 가상 스크롤로 고쳤다
  - 커밋 50만 개: commit-graph 파일이 없으면 `--topo-order`가 페이지마다 약 1.5~2초였다. 저장소를 열 때 없으면 한 번 만들도록 했고(약 2.4초, 백그라운드), 만든 뒤에는 첫 페이지 약 20ms, 25만 번째 커밋 근처 약 100ms, 마지막 페이지 약 190ms. 기록 마커(ref, 푸시 안 한 커밋, 들어올 커밋)는 약 35ms
  - 검색: 메시지 검색은 일치하는 게 없으면 전체를 훑어 약 1.7초, 코드 내용 검색(`-S`)은 약 22초, 경로 필터는 첫 페이지 약 3.5초. 검색어나 필터를 바꾸면 이전 git 프로세스를 취소한다(300ms 안에 끝남)
  - **남은 것**: 실제 앱(웹뷰)에서 끝까지 걸리는 시간은 직접 재지 않았다. Windows·Linux 측정
- [x] 앱 아이콘 자산: macOS Icon Composer/ICNS, Windows ICO, Linux PNG 및 재생성 스크립트
- [x] macOS 서명·공증, Windows 서명, Linux 패키지 (AppImage, deb)
  - 릴리스 워크플로(`.github/workflows/release.yml`): `v*` 태그를 푸시하면 세 OS를 빌드해 초안 Release에 올리고, 손으로 실행하면 Release 없이 설치 파일만 아티팩트로 남긴다. macOS는 유니버설(Apple Silicon + Intel) 빌드를 Developer ID로 서명하고 App Store Connect API 키로 공증한다. Linux는 AppImage와 deb(`git` 의존), Windows는 NSIS. MSI는 내지 않는다: 업데이터가 NSIS로 설치하고, 설치 파일이 둘이면 무엇을 받을지 헷갈리며 겹쳐 설치하면 앱이 두 벌 생긴다. MSI가 필요한 곳은 조직 일괄 배포인데 아직 수요가 없다. Microsoft Store의 무료 서명은 MSIX가 필요해 MSI와는 별개다
  - Windows는 v0.1에서 서명하지 않는다(SmartScreen 경고를 README에서 안내). SignPath Foundation(오픈소스 무료 서명)을 신청하고, Microsoft Store(MSIX)는 askpass 동작을 확인한 뒤에 검토한다
  - 수동 실행으로 확인함: 앱은 서명·공증·스테이플되고 유니버설(x86_64, arm64)이며, DMG도 따로 공증·스테이플해 내려받은 파일(quarantine)을 Gatekeeper가 받아들인다. Tauri는 DMG 안의 앱만 공증하므로 DMG 공증 단계가 필요하다
  - `v0.1.0-rc.1` 태그로 확인함(2026-10-22): 세 OS 빌드가 모두 성공해 초안 프리릴리스에 올라갔다. macOS 앱은 공증 Accepted, DMG는 스테이플 후 Gatekeeper가 `Notarized Developer ID`로 받아들였고, 공증한 DMG로 교체 업로드(`--clobber`)도 지나갔다. 업데이터 산출물(`.sig`, `latest.json`)도 함께 올라간다
  - `v0.1.0-rc.2`(2026-10-23): 첫 태그 푸시에서는 초안만 생기고 설치 파일이 하나도 올라가지 않았다. 초안을 만든 직후 릴리스 목록을 조회하면 새 초안이 아직 빠져 있어 id가 비었고, id가 비면 세 빌드가 업로드를 건너뛰면서도 성공으로 끝났다(rc.1은 운 좋게 잡혔다). 초안을 만드는 API 응답에서 id를 받고, 비면 `prepare`가 실패하도록 고쳤다. 빈 초안과 태그를 지우고 고친 커밋에 태그를 다시 달아 설치 파일이 올라가는 것을 확인했다(태그는 Garam의 태그 삭제·태그 푸시로 다뤘다)

## v0.1.x 패치

v0.1.0 이후 빈틈을 메운다. v0.1.1은 정식 릴리스끼리의 자동 업데이트 확인(M8)도 겸한다.

**v0.1.1 공개**(2026-10-23): 아래 네 항목을 담았다. `v0.1.1` 태그의 릴리스 워크플로가 세 OS 모두 성공했고, 올라간 파일은 v0.1.0과 같은 구성이다. 릴리스 노트(한국어·영어)를 넣어 공개했고, 업데이트 알림의 "새로운 기능"이 이 페이지를 연다. 늦게나마 v0.1.0 본문에도 릴리스 노트를 넣었다. 릴리스 수정 API는 `make_latest`를 주지 않으면 그 릴리스를 최신으로 바꾸므로, 지난 릴리스를 고칠 때는 `make_latest=false`를 준다(최신이 바뀌면 업데이트 피드가 옛 버전을 가리킨다).

- [x] 해결 결과가 빈 커밋이 되는 경우 안내(M7): 충돌을 모두 해결했는데 작업 폴더가 HEAD와 같으면, 배너가 "브랜치에 이미 같은 변경이 있다"고 알리고 "계속" 대신 "이 커밋 건너뛰기"(`--skip`)를 보여 준다. 체리픽과 되돌리기는 git이 빈 커밋을 만들지 않아 계속하기가 실패하고 멈춘 채로 남았다(중단밖에 길이 없었음). 리베이스는 git 2.54에서 계속하면 빈 커밋을 알아서 버리지만 같은 안내를 쓴다. 병합은 빈 병합 커밋이 정상이라 해당하지 않는다. 여러 커밋을 체리픽·되돌리기하다 다음 커밋도 비어 멈추면 오류 대신 같은 안내가 다시 나온다. 커밋하지 않은 변경이 있으면 건너뛰지 않는다(`--skip`이 작업 폴더를 되돌리므로)
  - 실제 앱에서 확인함(2026-10-23, macOS 개발 빌드): 체리픽 두 개가 차례로 비는 시험 저장소에서 건너뛰기 두 번으로 끝까지 진행된다
- [x] 다시 시작할 때 창 배치 복원(M1): 앱을 끝낼 때 열려 있던 저장소 창들을 같은 저장소, 같은 위치·크기, 최대화·전체 화면 상태로 다시 연다. 마지막으로 보던 창이 맨 앞에 온다. 창을 직접 닫으면 다음에 열지 않지만 마지막 창은 남는다. 목록에서 지운 저장소의 창과 잡을 수 없는 위치(연결이 끊긴 모니터)는 건너뛴다. 설정·정보 창은 복원하지 않는다(ARCHITECTURE.md 3장 "창 배치 복원")
  - 실제 앱에서 확인함(2026-10-23, macOS 개발 빌드): 창 여러 개를 ⌘Q로 끝내고 다시 열면 같은 저장소·위치·크기로 열리고, 직접 닫은 창은 열리지 않는다
  - **남은 확인**: 전체 화면, 모니터 두 대, Windows·Linux(메뉴의 끝내기)
- [x] 새 커밋이 쌓이면 commit-graph에 덧붙이기(M8 성능 점검): 저장소를 열 때와 가져오기·풀 뒤에, 그래프에 없는 커밋만 `--split` 층으로 덧붙인다. 커밋 50만 개 위에 2만 개가 쌓이면 첫 페이지가 10ms에서 40ms로 느려졌고, 덧붙이는 데 약 60ms(새 것이 없으면 약 10ms, 파일을 건드리지 않음)

  - 실제 앱에서 확인함(2026-10-23, macOS 개발 빌드): 블룸 필터가 있는 커밋 50만 개 저장소에서 경로 필터가 맞는 커밋을 바로 보여 준다

- [x] 파일과 diff: 추적 중인 파일은 기반 커밋과 스태시를 비교하고(`diff --name-status`), 추적하지 않는 파일은 세 번째 부모의 트리(`ls-tree`)에서 `ChangeKind::Untracked`로 더해 빈 내용과 비교한다
- [x] 보관: `git stash push [--include-untracked] [--message <메시지>] [-- <경로>…]`. 경로를 주면 리터럴 경로 그대로 동작한다(경로가 없을 때만 자동 보관처럼 `GIT_LITERAL_PATHSPECS=0`). 보관할 변경이 없으면 git이 스태시를 만들지 않으므로, 전후 `refs/stash`를 비교해 `nothing_to_stash`로 알린다
- [x] 적용·꺼내기: `git stash apply --index`(꺼내기는 성공한 뒤 `drop`). 실험한 경우별 처리:
  - 다른 내용과 충돌: 충돌한 파일이 작업 폴더에 남고 스태시는 그대로다(꺼내기도 지우지 않음). 오류 대신 `Conflicted` 결과를 돌려준다
  - 스테이지 상태를 되살릴 수 없음(`conflicts in index`): git이 아무것도 바꾸기 전에 멈추므로 `--index` 없이 다시 적용하고 `AppliedUnstaged`를 돌려준다. 내용은 잃지 않는다
  - 추적하지 않는 파일이 이미 있음: git은 추적 중인 파일 변경을 **먼저 적용한 뒤** 실패한다(처음 실험은 추적하지 않는 파일만 보관해서 몰랐다). 그래서 적용하기 전에 Garam이 겹치는 파일을 확인하고, 있으면 아무것도 하지 않고 `stash_untracked_exists`(자세히: 파일 목록)로 알린다
  - 커밋하지 않은 변경과 겹침: 기존 `local_changes_would_be_overwritten`. git이 아무것도 바꾸지 않는다
- [x] 여기서 브랜치 만들기: `git stash branch <이름> <스태시>`. 보관했던 커밋에서 새 브랜치를 만들어 꺼내므로 충돌하지 않는다. 적용이 막힐 때의 탈출구
- [x] 버리기·되살리기: `drop`, 그리고 `git stash store --message <스태시 커밋의 제목> <oid>`(객체는 gc 전까지 남아 있다). 되살린 스태시는 목록 맨 위로 온다
- [x] 모든 동작은 `stash@{n}` 대신 oid로 가리키고 실행 직전에 번호를 다시 찾는다(2.6과 같은 규칙). 이미 사라진 스태시는 `stash_not_found`
- [x] `TestRepo` 통합 테스트(`tests/stashes.rs`, 14개): 위의 경우마다 하나씩, 추적하지 않는 파일, 이름에 `*`·`[`가 든 파일만 골라 보관, 자동 보관과 섞인 목록, 다른 스태시가 생긴 뒤 oid로 찾기
- [x] 화면 쪽 정리: 기록 마커의 스태시(`log::stashes`)를 `stash::list`로 합치고, 스태시 파일의 이미지 비교 명령(`stash_images`)을 더했다

**제외**: 스태시 이름 바꾸기(git에 명령이 없고, 버린 뒤 다시 넣으면 순서가 바뀐다), hunk 단위 보관(`--patch`), 스태시를 버려서 잃은 커밋 찾기(`git fsck --unreachable`, 버리기의 실행 취소로 대신한다).

### Pull Request 연동 (v0.2)

Garam에서 바로 PR을 만들고, 브랜치가 어떤 PR과 이어져 있는지 본다. GitHub 계정 로그인(Device Flow, 키체인 토큰) 위에 얹는다. 호스팅 계층을 나눠 두어 v0.3의 GitLab Merge Request로 같은 화면을 잇는다.

- [ ] PR 만들기: 브랜치를 게시한 직후나 브랜치 메뉴에서 연다. 제목·본문은 커밋 메시지로 채우고(커밋이 하나면 그 요약과 본문), 기준 브랜치를 고르며, 브랜치 비교 화면(세 점 비교)을 미리 보기로 쓴다. 초안 PR 선택. 게시하지 않은 브랜치면 먼저 게시한다
- [ ] PR 상태: 브랜치 목록과 툴바에 PR 번호, CI 상태, 리뷰 상태 배지. 누르면 브라우저에서 PR을 연다
- [ ] PR 체크아웃: 다른 사람의 PR을 받아 내 컴퓨터에서 확인한다(포크의 PR 포함)
- **설계 메모**: 지금 OAuth scope로 PR을 만들 수 있는지 확인한다. scope를 넓히면 기존 사용자는 다시 로그인해야 하므로, 필요할 때 다시 로그인하라고 안내한다. 기본 원격이 github.com이 아니면 PR 기능을 숨긴다

### 히스토리 고도화 (v0.2 후보)

M6의 커밋 목록을 "지금 내 브랜치가 원격과 어떤 관계인지"까지 읽히는 화면으로 만든다. 비용이 작고 체감이 큰 것부터 한다. 한국어 UI에서는 "기록"이라고 부른다(GLOSSARY).

1. 위치 표시
   - [x] ref 배지: 커밋 옆에 로컬 브랜치·원격 브랜치·태그·분리된 HEAD. 같은 커밋을 가리키는 로컬·원격 브랜치는 배지 하나로 합친다. 현재 브랜치는 굵게
   - [x] 아직 푸시하지 않은 커밋 표시(업스트림이 있으면 `HEAD ^@{u}`, 없으면 `HEAD --not --remotes`, 원격이 없으면 표시 안 함)
   - [x] 아직 가져오지 않은 커밋(`@{u} ^HEAD`)을 목록 맨 위에 흐리게 표시. fetch 뒤 ahead/behind 숫자를 눈으로 확인한다
2. 검색과 필터
   - [x] 메시지·작성자·해시 검색(`--grep`, `--author`, 대소문자 무시·글자 그대로). git은 `--author`와 `--grep`을 AND로 묶으므로 검색 대상(메시지/작성자/코드)을 고른다. 메시지 검색에 16진수 7자 이상을 넣으면 그 커밋도 맨 위에 보여준다
   - [x] 코드 내용 검색(pickaxe `-S`)
   - [x] 경로 필터, 범위 선택(현재 브랜치 / 모든 브랜치와 태그 / 특정 브랜치), `--first-parent` 보기
   - [x] 검색창(⌘F / Ctrl+F, 입력이 300ms 멈추면 검색), 필터 팝오버, 결과가 없을 때 지우기 버튼. 필터는 저장소별로 탭을 오가도 유지한다
   - **남은 확인**: 대형 저장소에서 코드 내용 검색은 느리다(커밋 50만 개에서 약 22초). 새 검색을 시작하면 이전 git 프로세스는 취소한다(M8 성능 점검)
3. 커밋 동작
   - [x] 체리픽(메뉴). HEAD에서 이어진 목록에서는 이미 들어 있는 커밋이라 메뉴를 숨기고, 아직 풀하지 않은 커밋과 다른 범위에서만 보인다. 충돌하면 기존 충돌 배너로 이어지고, 바뀌는 게 없는 체리픽은 git이 진행 중으로 남기므로 중단하고 알린다
   - [x] 다른 브랜치로 체리픽(메뉴, 여러 커밋도): 대상 로컬 브랜치로 전환한 뒤 적용하고 그 브랜치에 남는다(GitHub Desktop과 같은 흐름). 작업 폴더가 깨끗해야 하고, 충돌하면 대상 브랜치에서 충돌 배너로 이어진다
   - [x] 체리픽을 브랜치로 끌어 놓기: 커밋 행(여러 개 선택했으면 모두)을 끌어 툴바 브랜치 버튼 위에 잠시 두면 브랜치 목록이 열리고, 로컬 브랜치에 놓으면 체리픽한다(현재 브랜치면 그대로, 다른 브랜치면 전환 후). 커서를 따라가는 표시와 브랜치 행·툴바 버튼의 강조로 어디에 놓일지 알려 주고(끌기가 다른 곳에서 시작되면 `:hover`가 따라오지 않는 웹뷰가 있어 끌기 상태로 직접 칠함) Esc로 취소한다. 창의 파일 드롭이 HTML 끌어 놓기를 가로채는 OS가 있어 포인터 이벤트로 직접 구현했다
   - [x] 끌어서 커밋 순서 바꾸기: 기록 목록 안에서 커밋(여러 개도)을 행 사이로 끌면 놓일 자리에 선이 보이고, 놓으면 그 순서로 다시 쌓는다. 현재 브랜치 줄의 최근 커밋에서 옮긴 가장 깊은 곳까지만 interactive rebase(`GIT_SEQUENCE_EDITOR`로 미리 만든 todo를 넣음)로 다시 쓴다. 병합 커밋이 섞이면 안 되고 작업 폴더가 깨끗해야 한다. 충돌하면 rebase 충돌 배너로 이어지고, 푸시한 커밋이 섞이면 강제 푸시 경고 대화상자를 거친다
   - [x] 이 커밋으로 리셋: 대화상자에서 스테이지 유지(soft) / 작업 폴더 유지(mixed) / 버리기(hard)를 고른다. hard는 위험 버튼과, 커밋하지 않은 변경 사항이 있으면 몇 개가 사라지는지 알린다
   - [x] 마지막 커밋 취소: HEAD이고 아직 푸시하지 않았을 때(원격이 없으면 언제나), 병합 커밋이 아닐 때만. 변경 사항은 스테이지된 채로 남고 메시지는 커밋 폼에 다시 채운다. 그사이 HEAD가 바뀌었으면 거부한다. 첫 커밋도 취소할 수 있다(태어나지 않은 브랜치로 돌아감)
   - [x] 이 커밋으로 전환(분리된 HEAD 안내, "여기서 브랜치 만들기"로 바꿀 수 있음), 여기에 태그 만들기(메시지를 쓰면 annotated). 태그 푸시는 v0.2 태그 관리에서
   - [x] 태그를 푸시와 함께 보내기: 앱에서 만든 태그는 저장소별 "아직 푸시하지 않은 태그" 목록(`.git/garam/unpushed-tags`, 워크트리끼리 공유)에 남고, 다음 푸시·게시가 브랜치와 함께 하나씩 이름을 지정해 보낸다(lightweight 태그도 가고, 가져온 태그나 터미널에서 만든 태그는 건드리지 않음). 보낼 커밋이 없어도 태그가 있으면 푸시 버튼이 켜지고 태그 수를 보여 준다. 원격에 같은 이름의 태그가 다른 커밋에 있으면 거부되고 목록에 남는다(`remote_tag_exists`). 가져온 태그도 로컬 `refs/tags`에 섞이므로, 원격에 묻지 않고 어느 태그가 원격에 없는지 알 방법이 없어 목록으로 기억한다
   - [x] 태그 삭제: 커밋 오른쪽 클릭 "v1 태그 삭제…"(확인 대화상자). 푸시한 적이 있을 수 있는 태그는 "origin에서도 삭제"를 고를 수 있다(기본은 끔, 원격을 먼저 지우고 로컬을 지움). 남겨 두면 다음 가져오기에서 다시 생길 수 있다고 알린다. 원격에 이미 없는 태그는 삭제된 것으로 친다
   - **남은 것**: 터미널에서 만든 태그를 푸시하는 방법(태그 배지 메뉴 "원격에 푸시" 등), 태그 목록 화면
4. 커밋 그래프
   - [x] 레인 계산과 그리기. git은 `--topo-order`로 자식을 부모보다 먼저 주고, 레인은 프론트(`features/history/graph.ts`)가 불러온 행 전체로 계산한다. 페이지가 늘어도 같은 함수로 이어지므로 페이지 사이 상태를 따로 넘기지 않는다. 레인은 옆으로 밀리지 않고, 10개를 넘으면 잘린다. 그래프 칸 너비는 행마다 그 행이 쓰는 레인만큼이라, 나중에 불러온 넓은 구간 때문에 위쪽 행에 빈 여백이 생기지 않는다
   - [x] 검색어나 경로 필터가 있으면 그래프를 그리지 않는다(검색은 최신순, 경로 필터는 부모를 건너뛴다). "첫 번째 부모만" 보기에서는 다른 부모 선을 그리지 않는다
   - [x] 커밋하지 않은 변경 사항 행(WIP, 점선으로 HEAD에 이어짐, 선택하면 변경 사항 탭으로 가는 버튼), 스태시 행(기반 커밋 바로 위, 점선. 선택하면 추적 중인 파일의 변경 내용)
   - **남은 확인**: 스태시의 추적하지 않는 파일은 아직 보여주지 않는다(스태시 관리에서). `--topo-order`가 전체를 훑지 않도록 저장소를 열 때 commit-graph 파일이 없으면 만든다(M8 성능 점검)
5. 커밋 상세 보강
   - [x] Conventional Commits 접두어(`type(scope)!:`)를 목록과 상세에서 조용한 배지로. 알려진 타입(feat, fix, docs 등 11개)만 인식해 `Merge: x` 같은 요약을 잘못 잡지 않는다. `!`나 `BREAKING CHANGE:` 꼬리말은 상세에 "호환성이 깨지는 변경"으로
   - [x] 서명 검증 배지(`%G?`). gpg를 실행할 수 있어 상세를 연 뒤 따로 확인한다. Co-authored-by 꼬리말은 본문에서 빼고 "공동 작성자"로
   - [x] 본문의 `#123`을 이슈·PR 링크로, 원격에서 커밋 열기(상세 버튼, 메뉴). 기본 원격이 github.com일 때만, 아직 푸시하지 않은 커밋은 열지 않는다. 다른 호스팅은 v0.3
   - [x] 공백 무시(`--ignore-all-space`, 커밋을 옮겨 다녀도 유지), 이미지 전후 비교(변경 사항 탭과 같은 화면), 패치로 복사·저장(`git format-patch`, 병합 커밋은 첫 번째 부모 기준)
   - [x] diff 구문 강조: GitHub Linguist 기준으로 파일 이름·확장자·shebang에서 언어를 고르고(Shiki 문법이 있는 약 300개 언어, 없는 언어는 일반 텍스트), Shiki를 지연 로딩해 색을 입힌다. 단어 단위 표시와 겹쳐 그린다(변경 사항 탭과 기록 모두)
   - [x] 단어 단위 diff: 삭제된 줄 묶음 바로 뒤에 추가된 줄 묶음이 오면 n번째끼리 짝지어, 낱말 단위 LCS로 바뀐 부분만 줄 여백과 같은 진한 색으로 표시한다(변경 사항 탭과 기록 모두). 너무 길거나(낱말 300개 초과) 60% 넘게 다른 줄은 표시하지 않는다
6. 비교와 복구
   - [x] 커밋 두 개 사이 diff: ⌘클릭(Windows·Linux는 Ctrl+클릭)이나 오른쪽 클릭 메뉴 "선택한 커밋과 비교". 목록에서 아래쪽(오래된) 커밋이 기준이 된다. 오른쪽 클릭은 선택을 바꾸지 않는다
   - [x] 브랜치 비교: 브랜치 메뉴 "브랜치 비교…", 기록 탭 검색창 옆 버튼, 브랜치 목록 아래 버튼, 브랜치 목록의 오른쪽 클릭 "현재 브랜치와 비교"(원격 브랜치도, 바로 세 점 비교로). 기준·대상을 자유롭게 고른다(기본은 현재 브랜치가 기준, 분리된 HEAD도 고를 수 있음). 비교 방식은 "갈라진 뒤의 변경"(세 점, `base...target`, PR과 같음)과 "두 쪽의 차이"(두 점). 비교 화면에서 방식 전환과 기준·대상 바꾸기를 바로 할 수 있다(커밋 비교에도). 양쪽에만 있는 커밋 수와 대상 쪽 커밋 몇 개를 보여준다. 이름은 전체 ref(`refs/heads/x`)나 커밋 id만 받는다
   - [x] 잃어버린 커밋 복구: 저장소 메뉴 "잃어버린 커밋 복구…". HEAD reflog 최근 500개 중 어느 브랜치·태그·원격 브랜치·HEAD에도 없는 커밋을 찾고, 한 줄기에서는 가장 최근 것만 보여준다(`merge-base --independent`). "보기"로 내용을 확인하고 "브랜치 만들기"로 되살린다. 아무것도 지우지 않는다
   - **남은 것**: 스태시를 버려서 잃은 커밋(reflog에 없음, `git fsck --lost-found`)은 찾지 않는다
7. 여러 커밋 선택
   - [x] ⌘클릭(Ctrl+클릭)으로 하나씩, Shift+클릭·Shift+↑↓로 범위. 커밋 행만 여러 개 고를 수 있다(변경 사항·스태시 행은 혼자). 오른쪽 클릭은 선택을 바꾸지 않는다
   - [x] 두 개 이상 고르면 오른쪽 창에 "커밋 N개 선택됨": 가장 오래된 커밋 바로 전부터 가장 최근 커밋까지 바뀐 내용(비교 화면의 심화판). 두 커밋 상태를 맞대는 비교는 하나만 골랐을 때 메뉴 "선택한 커밋과 비교"로 남는다
   - [x] 여러 커밋 체리픽(오래된 것부터, 이미 들어 있는 커밋은 `--skip`으로 건너뛰고 몇 개인지 알림), 되돌리기(최신 것부터), 충돌하면 기존 충돌 배너로 이어진다
   - [x] 스쿼시: 현재 브랜치의 첫 번째 부모 줄에서 이어진 커밋, 그 사이와 뒤에 병합 커밋이 없을 때만. `commit-tree`로 가장 최신 커밋의 트리와 가장 오래된 커밋의 작성자를 써서 하나로 만들고, 뒤의 커밋은 `rebase --onto`로 다시 쌓는다(이때는 작업 폴더가 깨끗해야 함). 메시지를 고치는 대화상자, 푸시한 커밋이 섞이면 강제 푸시 경고, "잃어버린 커밋 복구"로 되돌릴 수 있다는 안내

### GitHub 계정 로그인 (v0.2 후보)

버튼 하나로 브라우저에서 GitHub에 로그인하고, 여러 계정을 등록해 저장소마다 골라 쓴다. 지금은 HTTPS 원격에서 개인 액세스 토큰을 직접 붙여 넣어야 한다(M5의 자격 증명 대화상자).

목표 상황: 회사 Mac(전역 설정은 회사 계정·회사 이메일)에서 개인 프로젝트를 할 때, 저장소에서 개인 계정을 고르면 push 자격 증명과 커밋 작성자가 함께 바뀐다.

- [x] 저장소별 작성자: 커밋 영역에 작성자를 표시하고, "전역 설정 사용 / 이 저장소에서는 다른 작성자 사용"을 고른다. 저장소의 `.git/config`(`git config --local`)에 저장하므로 터미널에서 커밋해도 같은 작성자가 쓰인다
- [x] GitHub OAuth App 등록 (Device Flow 사용, 만료 토큰 끔). client ID는 `garam-github`의 `CLIENT_ID`
- [x] OAuth Device Flow 로그인: 버튼 → 일회용 코드를 클립보드에 복사하고 `github.com/login/device`를 시스템 브라우저로 연다 → 앱은 승인될 때까지 폴링
- [x] 토큰을 OS 키체인에 계정별로 저장 (macOS 키체인, Windows 자격 증명 관리자, Linux Secret Service)
- [x] 계정 목록·추가·로그아웃 (설정 → 계정), 계정 정보(로그인 이름, 아바타, 인증된 이메일)는 GitHub API로 가져온다
- [x] 저장소별 계정 선택: 커밋 영역의 작성자 줄 → "이 저장소의 계정과 작성자". 원격 URL의 사용자 이름 → 소유자 → 작성자 이메일 순으로 추천하고, 선택은 저장소 목록(`repositories.json`)에 저장
- [ ] 조직 멤버십으로 추천 (`read:org`, 원격 소유자가 조직일 때)
- [x] 선택한 계정의 토큰을 git에 넘기기 (credential helper, ARCHITECTURE.md 2.10). fetch·pull·push·게시와 백그라운드 fetch에 적용
- [x] 계정과 작성자 연결: 저장소에 계정을 고르면 그 계정의 인증된 이메일(`/user/emails`)과 noreply 주소 중에서 작성자 이메일을 고르게 한다
- [x] 불일치 경고: 저장소에 연결한 계정과 작성자 이메일이 맞지 않으면 커밋 영역과 대화상자에 알린다(예: 개인 계정으로 push하는데 작성자가 회사 이메일). 커밋을 막지는 않는다
- [ ] 복제할 때 계정 고르기 (지금은 복제 후 저장소에서 고른다)
- [ ] SSH 원격의 계정별 키 (`core.sshCommand`). 지금은 SSH 원격이면 계정 대신 SSH 설정을 따른다고 안내만 한다
- [ ] GitHub Enterprise Server 호스트 지원

**설계 메모**

- **Device Flow를 쓰는 이유**: 웹 플로(브라우저 → loopback 리디렉션)는 토큰 교환에 client secret이 필요한데, 오픈소스 앱에 넣으면 공개된다. Device Flow는 client ID만으로 동작하고 GitHub CLI도 이 방식을 쓴다. 사용자가 코드를 붙여 넣는 단계가 하나 더 있지만, 코드를 미리 클립보드에 넣어 두면 부담이 작다.
- **토큰 전달**: askpass보다 **credential helper**가 맞다. 사용자의 osxkeychain 같은 도우미에 다른 자격 증명이 저장돼 있으면 git이 askpass를 부르지 않기 때문이다. 네트워크 작업에 `-c credential.https://github.com.helper=`(목록 초기화)와 `-c credential.https://github.com.helper=<garam 실행 파일>`을 붙이고, askpass처럼 앱 실행 파일을 credential helper 모드로 실행해 작업 ID로 계정을 찾아 토큰을 돌려준다. 계정이 없는 저장소는 지금처럼 사용자 설정을 그대로 쓴다.
- **보안 원칙 변경**: ARCHITECTURE.md 7장의 "자격 증명은 앱이 저장하지 않는다"를 "앱이 발급받은 GitHub 토큰만 OS 키체인에 저장한다"로 바꿔야 한다. 토큰은 파일·로그·프론트로 보내지 않는다.
- **만료 토큰을 쓰지 않는다**: OAuth App의 "Expire user access tokens"는 끈다. 만료 토큰은 refresh token으로 갱신해야 하는데, 갱신 요청에 client secret이 필요해 Device Flow를 고른 이유가 사라진다. 대신 키체인 저장, 최소 scope, 로그아웃 시 폐기로 위험을 줄인다.
- **다른 credential helper와 함께 쓰기**: 사용자가 이미 `gh auth git-credential`이나 osxkeychain을 쓰고 원격 URL에 사용자 이름(`https://jihun-io@github.com/...`)을 넣어 계정을 구분할 수도 있다. 계정을 고르지 않은 저장소에서는 이 설정을 건드리지 않는다.
- **새 의존성**: HTTPS 클라이언트(`reqwest`, rustls)와 키체인 접근(`keyring`). 토큰을 GitHub에서 폐기하는 API(`DELETE /applications/{client_id}/token`)는 client secret이 필요해 앱이 직접 부를 수 없다. 그래서 로그아웃은 키체인에서 토큰을 지우고, 권한까지 취소하려는 사용자를 GitHub 설정 페이지로 안내한다.
- **테스트**: Device Flow와 API는 목 서버로, credential helper 프로토콜은 `git credential fill`로 통합 테스트한다.
